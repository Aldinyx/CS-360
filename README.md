# Briefly summarize the requirements and goals of the app you developed. What user needs was this app designed to address?
The goal of the app I developed was to be an event tracker. This meant that the app needed to allow users to add, edit, and remove events from a list of events that remains persistent even if the user closes and reopens the app. Another goal of the app was to have a user login where users would enter a valid username and password combination or create a new login before accessing the app's main features. The app was also required to send an SMS notifications on the day of an event, regardless of whether the app was currently open. Overall, this app was meant to address the user needs of keeping track of events and setting simple reminders.
# What screens and features were necessary to support user needs and produce a user-centered UI for the app? How did your UI designs keep users in mind? Why were your designs successful?
The screens that were necessary to support the needs of the user were a login screen for handling user login and account creation, the main events screen where the list of the user's current events are displayed, and a screen for entering the details of a new event or editing the details of an existing event. I produced user-centered UI for the screens by making the flow between screens logical and the elements for navigation obvious. For example, the button to add a new event is a denoted with a plus symbol, a well-established symbol for addition. Along with this, while the screen for editing event details and adding a new event is the same, a button for deleting the current event is hidden when adding a new event as opposed to editing an existing one. This improves usability by removing unnecessary options.

Perhaps most notably, the process for asking permissions from the user is incredibly streamlined. Permissions are needed to access the device's features required to send SMS messages. Rather than being having the user navigate to a separate screen, these permissions are automatically requested upon logging in and navigating to the main events screen. This ensures the options are not hidden and also means the permissions can be cleanly requested once and then stay out of the user's way on subsequent uses of the app.

My designs were successful because all of the required features were implemented, and the options available to the user on any given screen are clear. On top of this, the app makes decent use of contrasting colors to add visual flair and communicate what parts of the screen are interactable.
# How did you approach the process of coding your app? What techniques or strategies did you use? How could those techniques or strategies be applied in the future?

# How did you test to ensure your code was functional? Why is this process important, and what did it reveal?
To test if my code was functional I ran the app many times, first by emulating it in Android Studio and then eventually by running it on my smartphone. This process was crucial as it revealed several bugs and errors in logic. For example, my implementation of the saving and loading feature for the app's event list involved populating the list every time the main event screen activity is resumed. However, my intial implementation also involved loading events from a database into the list every time the activity was resumed without first clearing the existing elements in the list, which often resulted in the events in the list duplicating.

Testing the app also allowed me to confirm when certain features were working as intended. Without testing, it would be very difficult to be certain that permissions were being requested for correctly, that the app would continue to work even if permissions were denied, or if the app could successfully send SMS notifications to the device's phone number.
# Consider the full app design and development process from initial planning to finalization. Where did you have to innovate to overcome a challenge?
During the app's design and development process, I had to iterate several times to overcome a challenge. One example of this was in implementing the requests for permissions. In one of my original designs, I planned on permissions being requested on a separate screen with tailor-made accept and deny buttons. However, it became more practical and user-friendly to simply ask for permissions using standard permission request dialogs that most users would be familiar with.

Another example of needing to innovate to overcome a challenge was in implementing the SMS notification feature. Since this feature required SMS notifications to be sent on the day of an event regardless of whether the app was currently open, it meant that a task needed to run in the background. There were a number of possible ways to do this, but I eventually settled on using a loop that starts running upon logging in and navigating to the main events screen. This loop checks the current date against the dates for the saved events once every minute and sends a notification for each event with a match.
